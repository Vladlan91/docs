## Überblick

Der Workflow-Editor ist ein visuelles, knotenbasiertes Werkzeug zur Gestaltung von Konversationslogik. Ziehen, platzieren und verbinden Sie Knoten, um komplexe Konversationsabläufe zu erstellen.

## Knotentypen

### Start-Knoten
Der Einstiegspunkt für jeden Workflow. Jeder Workflow hat genau einen Start-Knoten.

### LLM-Knoten
Sendet eine Nachricht an das konfigurierte KI-Modell und gibt die Antwort zurück.

**Einstellungen:**
- Temperatur (0,0 - 1,0)
- Maximale Tokens
- Benutzerdefinierte System-Prompt-Überschreibung

### Bedingungs-Knoten
Verzweigt den Workflow basierend auf Bedingungen. Unterstützt:
- Schlüsselwort-Abgleich
- Sentimentanalyse
- Benutzerdefinierte Ausdrücke

### Tool-Aufruf-Knoten
Führt eine externe Funktion oder einen API-Aufruf aus. Ergebnisse werden an den Konversationskontext zurückgegeben.

### Sprachanruf-Knoten
Verarbeitet sprachspezifische Interaktionen — Spracherkennung und -synthese.

### End-Knoten
Beendet die Konversation mit einer optionalen Abschlussnachricht.

## Knoten verbinden

Klicken Sie auf den Ausgangsport eines Knotens und ziehen Sie zum Eingangsport eines anderen Knotens, um eine Verbindung zu erstellen. Jede Verbindung stellt einen möglichen Konversationspfad dar.

## Best Practices

<Tip>
  Erstellen Sie immer explizite Pfade zwischen Knoten mit klaren Bedingungen. In einigen Fällen kann die KI jedoch eigenständig zu einem Knoten routen, der keine direkte Kante hat — dies wird als **Synapse** bezeichnet. Synapsen treten auf, wenn die KI feststellt, dass bestehende Routing-Bedingungen unklar oder unzureichend sind, und selbst entscheidet, einen Knoten zu erreichen. Obwohl dies Flexibilität bietet, deuten häufige Synapsen in der Regel darauf hin, dass Ihre Kantenbedingungen spezifischer sein müssen.
</Tip>

- Halten Sie Workflows einfach — komplexe Abläufe sind schwieriger zu debuggen
- Verwenden Sie Bedingungs-Knoten für Sonderfälle
- Testen Sie jeden Pfad einzeln, bevor Sie veröffentlichen

## Workflow mit Claude Code generieren

Wenn Sie einen benutzerdefinierten Workflow für Ihren AI-Agenten basierend auf Ihren Geschäftsanforderungen erstellen möchten, können Sie **Claude Code** verwenden, um eine gebrauchsfertige Workflow-Vorlage als JSON zu generieren.

<Accordion title="Prompt zur Workflow-Generierung">
```text
# Anleitung: Revol Workflow-Vorlage als JSON generieren

## Kontext

Ich verwende Revol — eine Plattform zur Erstellung von
AI-Vertriebsagenten. Jeder Agent hat einen visuellen
Workflow-Editor mit Nodes und Edges, die die
Konversationslogik definieren.

Ich benötige eine Workflow-Vorlage als JSON-Objekt, das ich
in meinen Revol-Agenten importieren kann. Das JSON folgt
einem strikten Schema des Revol-Template-Systems.

## JSON-Schema

Die Ausgabe muss ein einzelnes JSON-Objekt mit diesen
Schlüsseln sein:

{
  "nodes_data": [...],
  "edges_data": [...],
  "tools_data": {...},
  "memory_fields_data": [...]   // optional
}

### nodes_data (Array von Objekten)

Jedes Node-Objekt hat diese Felder:

| Feld | Typ | Pflicht | Beschreibung |
|------|-----|---------|-------------|
| index | integer | ja | Eindeutiger Index (ab 0), für Edge-Referenzen |
| node_type | string | ja | Einer von: start, custom, system_stt, system_tts, system_product, system_media, system_company, system_formatter |
| name | string | ja | Anzeigename auf dem Canvas |
| position_x | integer | ja | X-Koordinate auf dem Canvas |
| position_y | integer | ja | Y-Koordinate auf dem Canvas |
| is_active | boolean | ja | Ob der Node aktiv ist |
| conversation_goal | string | nein | System-Prompt für diesen Node (nur custom Nodes) |
| config | object | nein | Node-spezifische Konfiguration (siehe unten) |
| llm_provider_override | string | nein | LLM-Provider überschreiben: openai, anthropic, gemini, groq |
| llm_model_override | string | nein | Modellname überschreiben |
| temperature_override | number | nein | Temperature überschreiben (0.0-2.0) |

Node-Typen und ihre Aufgabe:
- start — Einstiegspunkt, genau einer pro Workflow, kein conversation_goal
- custom — LLM-Node mit eigenem Prompt, Tools und Wissensdatenbank
- system_product — Produktsuche, Verfügbarkeitsprüfung, Details
- system_media — Abruf von Fotos, Videos, Dokumenten
- system_company — Firmeninformationen und Support
- system_formatter — kombiniert Ergebnisse paralleler Nodes zur finalen Antwort
- system_stt — Spracherkennung (Spracheingabe), standardmäßig inaktiv
- system_tts — Sprachsynthese (Sprachausgabe), standardmäßig inaktiv

Config für system_stt:
{
  "provider": "openai",
  "language": "de",
  "greeting_text": "Hallo! Wie kann ich Ihnen helfen?",
  "greeting_audio_url": null,
  "farewell_text": "Danke! Auf Wiedersehen!",
  "farewell_audio_url": null
}

Config für system_tts:
{
  "provider": "openai",
  "voice": "nova",
  "model": "tts-1",
  "speed": 1.0
}

Config für custom Nodes (optional):
{
  "save_to_memory": ["field_key1", "field_key2"],
  "max_tool_rounds": 3,
  "tool_timeout_seconds": 30
}

### edges_data (Array von Objekten)

Jedes Edge-Objekt verbindet zwei Nodes:

| Feld | Typ | Pflicht | Beschreibung |
|------|-----|---------|-------------|
| source_index | integer | ja | Index des Quell-Nodes |
| target_index | integer | ja | Index des Ziel-Nodes |
| condition_type | string | ja | Einer von: always, keyword, intent, state, fallback |
| condition_value | object | nein | Bedingungsparameter (null für always/fallback) |
| priority | integer | nein | Auswertungspriorität (Standard: 90 für always) |

Bedingungstypen und Prioritäten:
- keyword (Priorität: 100) — Wortübereinstimmung in der Nachricht
  condition_value: { "keywords": ["Wort1", "Wort2", ...] }
- state (Priorität: 95) — prüft Speicherfeldwerte
  condition_value: { "conditions": [{"field": "name", "operator": "filled|empty|=|!=|contains|>|<", "value": ""}] }
- always (Priorität: 90) — bedingungslos, ermöglicht parallele Verzweigung
  condition_value: null
- intent (Priorität: 50) — LLM klassifiziert die Nachrichtenabsicht
  condition_value: { "intents": ["intent_name"] }
- fallback (Priorität: 10) — greift nur wenn nichts anderes passt
  condition_value: null

### tools_data (Objekt, Schlüssel sind Node-Indizes als Strings)

Ordnet Node-Index einem Array von Tool-Namen zu:

{
  "2": ["search_documents", "get_company_info"],
  "3": ["get_products", "get_product_details"]
}

Verfügbare eingebaute Tools (9):
- get_products — Produktsuche nach Name/Beschreibung
- get_product_details — Vollständige Details eines Produkts
- check_availability — Verfügbarkeitsprüfung
- search_by_parameters — Produkte nach Attributen filtern
- get_company_info — Firmenname, Beschreibung, Kontakte
- search_documents — Semantische RAG-Suche in der Wissensdatenbank
- get_photos — Fotos abrufen
- get_videos — Videos abrufen
- get_documents — PDF/Word/Excel-Dateien abrufen

### memory_fields_data (optionales Array)

Definiert strukturierte Felder, die der Agent sammeln soll:

[
  {"key": "client_name", "label": "Kundenname", "type": "text"},
  {"key": "client_phone", "label": "Telefon", "type": "phone"},
  {"key": "topic", "label": "Thema", "type": "select", "options": ["Verkauf", "Support"]}
]

Feldtypen: text, phone, email, number, select (mit options-Array).

## Workflow-Muster

### Muster 1: Einfach (ein Experte)
Start → Custom Node → Formatter
Geeignet für: FAQ-Bots, einfacher Support, Einzelthema-Agenten.

### Muster 2: Parallele Experten (always-Routing)
Start → Experte A → Formatter
      → Experte B → Formatter
      → Experte C → Formatter
Geeignet für: Agenten die gleichzeitig Produkte + Dokumente + Firmeninfo durchsuchen.

### Muster 3: Smart Router (intent/keyword-Routing)
Start → (intent: sales) → Verkaufsexperte → Formatter
      → (intent: support) → Supportexperte → Formatter
      → (fallback) → Allgemeiner Experte → Formatter
Geeignet für: Multithema-Agenten mit unterschiedlicher Expertise pro Frage.

### Muster 4: Lead-Sammlung (state-Routing)
Start → (Name leer) → Name sammeln → Formatter
      → (Name gefüllt, Telefon leer) → Telefon sammeln → Formatter
      → (alles gefüllt) → Abschlussantwort → Formatter
Geeignet für: Lead-Qualifizierung, Terminbuchung, Formularflüsse.

### Muster 5: Voice-Agent
STT → Start → Experte → Formatter → TTS
Wie jedes obige Muster, aber mit aktiven STT/TTS-Nodes.

## Layout-Richtlinien

- Start-Node auf Position (0, 0)
- STT-Node links: (-200, 0)
- Experten-Nodes rechts: (200, -100), (200, 0), (200, 100)
- Formatter weiter rechts: (400, 0)
- TTS-Node ganz rechts: (600, 0)
- Vertikaler Abstand zwischen parallelen Nodes: 100-200px

## Regeln

1. Jeder Workflow MUSS genau einen "start"-Node haben
2. Jeder Workflow MUSS genau einen "system_formatter"-Node haben
3. STT- und TTS-Nodes einbinden, aber is_active: false setzen,
   außer Voice wird explizit angefordert
4. Custom Nodes sollten einen klaren, fokussierten conversation_goal-Text haben
5. Jeder Custom Node sollte mindestens das Tool search_documents haben
6. Intent-Routing statt keyword für mehrsprachige Agenten verwenden
7. Der Fallback-Edge stellt sicher, dass keine Nachricht unbeantwortet bleibt
8. Node-Indizes müssen sequenziell ab 0 sein
9. Alle source_index und target_index in Edges müssen auf gültige Node-Indizes verweisen
10. conversation_goal sollte in der Sprache geschrieben werden, die der Agent verwendet

## Ausgabe

Gib NUR das JSON-Objekt zurück — kein Markdown, keine Erklärung,
keine Code-Blöcke. Das JSON muss valide und parsebar sein.

## Eingabe

Mein Unternehmen: [BESCHREIBEN SIE IHR UNTERNEHMEN]
Agentenrolle: [z.B. Verkaufsberater, Supportagent, Lead-Sammler]
Sprachen: [z.B. Deutsch, Englisch, mehrsprachig]
Voice aktiviert: [ja/nein]
Schlüsselthemen/Abteilungen: [z.B. Produkte, Abrechnung, technischer Support]
Speicherfelder zum Sammeln: [z.B. Name, Telefon, E-Mail, oder keine]
Besondere Anforderungen: [zusätzliche Anforderungen]
```
</Accordion>

<Tip>
  Nach der JSON-Generierung können Sie Node-Namen, Conversation Goals oder Tool-Zuweisungen überprüfen und anpassen, bevor Sie importieren. Das Workflow-Vorlagenformat wird in einem zukünftigen Revol-Update direkt importierbar sein.
</Tip>
